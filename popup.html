Bulk scan (beta)

    
Scans a range of BigCommerce order IDs using the store's subdomain entered above, and flags only the ones worth a closer look. Unlike Shopify's bulk scan, this only supports a continuous numeric range (not a comma-separated list) — BigCommerce's order-list range filter (orderFrom/orderTo) works on a from/to range, confirmed against real data to return every order in between in one fetch, not just the endpoints.

    
    
    
    
    

      
      
    

    

      

        

      

    

    

    

      

      

    

    
Fetches the order list once (capped at 100 orders per fetch — larger ranges aren't paginated automatically yet), then fetches each matched order's full details sequentially to run diagnostics. This is slower than Shopify's bulk scan, which gets everything in one call — BigCommerce has no single endpoint with both status and excise/address detail together. If "Find order by email" is filled in, every order in the range is checked against that email (not just ones with other issues) and shown separately below, so you can locate a specific order (e.g. from a support case) and see its verification status even when nothing else about it looks wrong.

Product & price check (beta)

    
Looks up each product by SKU via BigCommerce's internal catalog API — compares the charged price against the current listed price (same idea as Shopify's Live price check), and flags products with no product_tax_code set. On-demand, not automatic: one extra request per unique product on the order, and an empty tax code doesn't necessarily mean a bug — it can also mean the product is genuinely non-taxable, or just hasn't been configured in TOT yet. Use judgment on the result, same as PMD on the Shopify side.

Product & price check (beta)

    
Compares each line item's charged price against the product's current WooCommerce price (_regular_price / _sale_price) — same idea as BigCommerce's and Shopify's live-price checks. This does NOT check TOT's own retailPrice/wholesalePrice/msrp fields: those are pushed to/pulled from HQ's API directly and aren't stored as WooCommerce postmeta, so there's nothing on this page to read them from. Variable products are skipped (informational only) since the parent product's page doesn't expose the specific variation's price. A mismatch can also mean the price changed since the order, a coupon was applied, or the order used wholesale pricing this check can't see — use judgment, same as the other platforms' product checks.

HQ Excise Tax scan

    

      Automates the Active Monitoring sweep against HQ's Excise Tax Order API: opens a tab on HQ, switches to each org below, verifies it's scoped to that org, then checks recent orders for the error.incorrectCollection pattern (tax owed but not collected). Rides your own logged-in HQ session — doesn't create or store separate credentials, and can't run unattended.
    

    

      Requires the scripting and tabs permissions plus https://app.tokenoftrust.com/* host access.
    

  


  

    
Scan queue

    
Each row is one org. Three ways to scope a row: an ID start + end (fixed range), an ID start with no end (scans forward from there and auto-stops once it stops finding real orders — use this when you know where to start but not what the newest order number is), or check the time-window box to scan by hours-ago instead (defaults to 24, editable up to 336 / 2 weeks — bump it past 24 to cover a weekend or other gap the ID-range mode's auto-stop skipped). Checking it clears the ID range fields.

Product data backfill

    

      Cross-references HQ's excise-tax "missing data" list against the store's real BigCommerce catalog and TOT's already-completed records for the same product family, fills in whatever's genuinely derivable (never guessed from titles/descriptions), and exports a CSV in HQ's upload format for you to review and upload yourself — it never uploads anything automatically. Misclassified items (e.g. a "Nicotine Pouches" product filed as "vape") go to a separate review list instead of being marked complete under the wrong type. A value derived from a sibling product is filled in but flagged in NOTES for a quick check, never silently confirmed. Anything it can't derive gets a note in a trailing NOTES column instead of a guess. Items with no name/SKU anywhere are skipped by default.
    

    

      Needs a fresh access token pasted from DevTools each run (see README for the steps) — this is a separate auth system from the Product Sync API.

Completely unclassified records are skipped, not checked — see the note above.

Order Investigation

    

      Calls HQ's GET /api/exciseTax/orders/{appTransactionId}/investigation — one read-only call that returns the full evidence for an order: what was collected vs. what TOT calculated at checkout, at record time, and under current rules; the resolved jurisdiction; which rules fired; per-product metadata drift; and a verdict. Replaces the manual calc-detail parsing and state rate table lookups from the HQ Excise Tax Scan tab — use it for one-off "why was this order wrong" investigations, like the 2448091 case.
    

    

      Uses a separate, more sensitive credential: an ops.tokenoftrust.com API key/secret pair with api:opsAdmin, gated behind diagnostic:investigate (a regular signed-in HQ session can't mint this). Stored only in local extension storage, never logged or exported, and sent only as the Authorization header to app.tokenoftrust.com.

Verification Diagnostics (beta)

    

      Calls HQ's POST /api/diagnostic/evaluate — the same self-describing diagnostic function API documented at /hq/api-docs/diagnostic that the Ops "VerifOps" Trello epic is built around. Of its 19 functions, 8 are already wired into VEX (Verification Explorer); the two below — lookupVerificationAttempt and verificationHealthCheck — are exposed but reachable nowhere Ops can get at today, per that epic's own API coverage assessment. No new API work needed here, only UI wiring on top of an endpoint that already exists.
    

    

      Reuses the same ops.tokenoftrust.com API key/secret entered on the Order Investigation tab (evaluate needs diagnostic:read, plus diagnostic:crossTenant for any domain other than the key's own). Whether that key actually carries diagnostic:read/diagnostic:crossTenant is genuinely unconfirmed — the epic's own Uncertainty #1 notes its absence reads as "no data found", not "no permission" (i.e. a clean-looking empty result can silently mean the wrong thing). Running either check below against a known real case is the actual live test for that, not an assumption baked in ahead of it.
    

  


  

    
Look up a verification attempt code

    
Resolves the 6-character code shown in a verification modal's footer to the journey behind it — appDomain, appUserid, sessionUuid, and the reuse chain (sourceVerificationAttemptId) when the attempt reused a prior verification. Per the epic: "the most common intake artifact, and Ops cannot resolve one today."

Tax Rules API (PRODUCTION — live data)

    
Reads, previews (dry-run) and saves the global excise tax rules on production (app.tokenoftrust.com). The host is hard-coded — this tab cannot talk to the test server. A saved change applies to every live vendor that has not overridden that jurisdiction; per-vendor overrides live in the Client Config API and are not covered here.

    
Every save captures a revert point first: the full rule set is snapshotted, and the previous value of each changed jurisdiction is logged so it can be restored in two clicks.
